# Производительность построения графа

Первый замер оптимизации PBF-декодирования на Apple M4, Go 1.27.2, локальной выгрузке
`northwestern-fed-district-latest.osm.pbf` около 625 МБ и области
`west=30.10811, south=59.80699, east=30.48226, north=59.93393`:

| Этап | До оптимизации | После оптимизации |
|---|---:|---:|
| Загрузка OSM в Dataset | 22,324 с | 12,141 с |
| Классификация и маршрутизация | 3,605 с | 3,564 с |
| Весь Build | 25,930 с | 15,706 с |
| Узлы / связи | 33 / 503 | 33 / 503 |

Это одиночные локальные замеры с доступным файловым кэшем ОС; они не гарантируют
такое же время на другой машине или области. Бенчмарк вызывает Build напрямую:
не использует кэш готовых графов и не включает скачивание, очередь и запись в БД.
Проверка полного HTTP-сценария выполняется отдельно.

PBF-фильтры отбрасывают ненужные точки и линии на уровне декодера, позволяя
переиспользовать память объектов. Предикаты читают только неизменяемые данные
текущего прохода: библиотека вызывает их из нескольких горутин. Дополнительный
проход для геометрии отношений выполняется только при отсутствии нужных линий.
Логи `OSM dataset loaded` и `build completed` показывают длительность чтения
OSM и всей обработки соответственно.

Для воспроизводимого замера без БД и кэша готовых графов из `backend`:

```sh
OSM_BENCH_FILE="$PWD/main/var/extracts/northwestern-fed-district-latest.osm.pbf" \
  go test ./tests/infrastructure/osm -run '^$' \
  -bench BenchmarkRegionalGraphBuild -benchtime=1x -count=1
```

Бенчмарк не скачивает данные. Он строит граф для фиксированной области южной
части Петербурга и отдельно показывает `osm_ms/op` и `graph_ms/op`.

После этого замера маршрутизация переведена на числовые индексы и массивы;
текущие значения могут отличаться от исторической таблицы. Для проверки всего
пресета добавьте `OSM_BENCH_REGION=spb-leningrad` к команде бенчмарка. Он занимает
заметно больше времени и памяти, чем построение маленькой области.

## Дальнейшее ускорение

Основная оставшаяся затрата — повторное последовательное чтение и распаковка PBF.
Уменьшение области снижает объём сохраняемых данных, но весь файл всё равно читается.

1. Импортировать OSM один раз в хранилище с пространственным индексом. Например,
   PostGIS с GiST по геометрии и выборкой через ST_Intersects. Хранить полную
   геометрию линий, идентификаторы точек и участников отношений, чтобы сохранять
   топологию. Версия импорта должна участвовать в ключе результата. Это следующий
   основной шаг, который позволит убрать полный проход по PBF из каждого запроса.
2. Кэшировать подготовленную транспортную сеть по источнику, версии и виду
   транспорта. Ограничить размер кэша и совместно использовать один процесс
   подготовки для одновременных заданий по соседним областям.
3. Продолжить профилирование маршрутизации полного региона. Числовые индексы
   и компактные списки смежности уже применены; следующий шаг следует выбирать
   по текущему профилю CPU и памяти.

Готовый граф для точно тех же границ и версии источника уже переиспользуется:
повторный POST возвращает HTTP 200 и graph_id без нового построения.

Long polling сокращает число HTTP-запросов и задержку получения статуса.
На время вычисления самого графа он не влияет.

Источник по пространственным запросам:
[PostGIS ST_Intersects](https://postgis.net/docs/ST_Intersects.html).

## Проверка всего пресета СПб и Ленобласти

Успешная проверка 21.10.2026 на том же Apple M4 и той же локальной выгрузке:

- исходный пространственный индекс: 23 601 762 идентификатора точек;
- Dataset: 353 628 линий, 2 360 177 вхождений точек в линии;
- дорожная сеть маршрутизации: 1 778 508 уникальных точек и 3 621 624 дуги;
- итог: 163 логистических узла, 17 304 направленные связи;
- полный цикл построения и сохранения: около 72 секунд;
- сохранённый JSON: 212 358 704 байта, 2 429 345 точек геометрии;
- получение и разбор полного графа через локальный HTTP: около 5,5 секунды;
- повторный POST для этого региона: HTTP 200 с существующим graph_id.

Замер включает упрощение длинных геометрий с допуском 10 м в метрической
проекции. Длины маршрутов рассчитаны по исходным линиям. Данные не включают
внешний справочник подтверждённых грузовых станций и отдельные морские/авиамаршруты.
Пресет задаёт прямоугольник, а не точные административные полигоны.

Полный граф остаётся большим ответом для браузера. Следующий отдельный шаг для
отображения — выдача геометрии видимой области и разделение загрузки метаданных,
узлов и связей. Сейчас эти отдельные API ещё не реализованы.
