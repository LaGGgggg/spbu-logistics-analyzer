# Архитектура backend

Имена прикладных сервисов отражают назначение и заканчиваются на `_service`.
Реализация хранения логистических данных называется `logistics_repository`;
PostgreSQL — технология её реализации.

## Слои и зависимости

| Директория | Ответственность |
|---|---|
| `backend/main.go` | Сборка зависимостей, запуск HTTP и воркеров, завершение процесса |
| `backend/internal/domain/logistics` | Граф, узлы, дуги, координаты, границы и грузовая политика |
| `backend/internal/domain/buildjob` | Состояния и сущность задания |
| `backend/internal/application/logistics_service` | Запуск и чтение результатов, выбор области, выполнение фоновых заданий |
| `backend/internal/application/graph_build_service` | Построение графа, объединение узлов, маршрутизация и пространственный индекс |
| `backend/internal/repository/logistics_repository` | Хранение регионов, графов и заданий в PostgreSQL |
| `backend/internal/repository/osm` | Чтение OSM, подбор источника, Overpass и кэширование выгрузок |
| `backend/internal/repository/config` | Чтение и проверка конфигурации запуска |
| `backend/internal/interfaces/httpapi` | Gin, HTTP-контракт, проверка запросов и преобразование ошибок |
| `backend/internal/interfaces/export` | CSV, матрицы, GeoJSON и GraphML |
| `backend/tests` | Тесты по слоям; имена тестовых директорий соответствуют рабочим пакетам |

HTTP зависит от входного прикладного интерфейса `logistics_service.Queries`.
Прикладной слой зависит от домена и объявляет исходящие порты `Repository`,
`AreaResolver` и `Source`. Внешние адаптеры реализуют эти порты; домен не зависит
от Gin, pgx и OSM-парсера. Конкретные компоненты связываются в `main.go`.

## Разделение файлов

В `logistics_service` сценарии чтения и запуска находятся в `logistics_service.go`,
работа с произвольной областью — в `area_build.go`, выполнение заданий — в
`build_worker_service.go`. Контракты отделены в `ports.go` и `repository.go`,
результаты и состояния — в `build_result.go`, ошибки — в `errors.go`.

В `graph_build_service` построение находится в `graph_build_service.go`,
объединение узлов — в `nodes.go`, маршрутизация — в `routing.go`,
пространственный индекс — в `spatial.go`, контракты — в `ports.go`.

| Файл в `logistics_repository` | Ответственность |
|---|---|
| `connection.go` | Создание, проверка и закрытие пула подключений, конструктор репозитория |
| `initialization.go` | Миграции, пресеты регионов, блокировка экземпляра, восстановление заданий |
| `regions.go` | Чтение регионов и сохранение произвольной области |
| `build_requests.go` | Дедупликация запросов и постановка задания |
| `graphs.go` | Чтение графов |
| `jobs.go` | Чтение, захват, ошибка и возврат задания в очередь |
| `build_completion.go` | Сохранение графа и завершение задания одной транзакцией |
| `errors.go` | Преобразование ошибок pgx в прикладные ошибки |

Пул подключений закрывается владельцем: после `Open` сервер вызывает `Close`;
при передаче существующего пула через `New` его жизненным циклом управляет вызывающий код.
Разделение файлов сохраняет атомарность завершения задания, дедупликацию запросов
и существующее поведение HTTP API.
